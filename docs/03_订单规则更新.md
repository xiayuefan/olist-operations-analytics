# 第 2 课收尾：把六条核查规则更新为八条

## 新检查的含义

你已运行并核对两个结果：可比较记录中审批早于下单为 0 笔，交物流早于审批为 1,359 笔。前者有 160 笔因时间缺失无法比较，后者有 1,797 笔无法比较，不能把这些记录当作顺序正常。

例如截图中的第一笔订单，下单为 2018-06-07，交物流为 2018-06-11，审批记录为 2018-06-12，交物流早于审批。这里能确认的是记录顺序与预期不符；具体原因需要源系统或业务信息，不能确定为未付款先发货。

计算审批后交物流耗时时，负值应标记并排除出该项有效耗时，不能通过取绝对值或改成零修正。它是否影响其他指标，按各指标需要的字段另行判断。

## 规则版本

| 项目 | v1：六条规则 | v2：八条规则 |
| --- | ---: | ---: |
| 保留订单数 | 99,441 | 99,441 |
| 规则触发次数 | 219 | 1,578 |
| 待核查订单数 | 218 | 1,411 |
| 运输有效样本数 | 96,281 | 96,281 |
| 延迟有效样本数 | 96,470 | 96,470 |
| 延迟订单数 | 6,534 | 6,534 |
| 延迟率 | 6.77% | 6.77% |

v2 在 v1 基础上增加：

- `flag_approval_before_purchase`：两端时间存在，且审批早于下单。
- `flag_carrier_before_approval`：两端时间存在，且交物流早于审批。

新的 `review_rule_count` 和 `flag_needs_review` 按八条规则重新计算。原六条规则的计数保持原定义。

**为什么新增关注订单只有 1,193 笔？**

新规则触发 1,359 笔，其中 166 笔已经在 v1 清单中，因此：

```text
v2 待核查订单 = 218 + 1,359 - 166 = 1,411
新增待核查订单 = 1,411 - 218 = 1,193
```

这是按订单去重后的并集数量，不是触发次数的累加。

## 为什么两个业务指标保持一致

这次改变的是核查清单范围，运输和延迟指标的有效样本规则继续使用课堂基线。核查标记不是统一删除条件。例如，审批时间有疑点，不足以直接确定实际送达日期或运输时间错误。

后续做敏感性分析时，会对比排除这些记录前后的结果，并同时说明样本量变化。目前不把 1,411 笔全部从业务指标中删除，也不把它们都认定为错误。

## 使用更新后的函数

`clean_orders` 和 `summarize_metrics` 都增加可选参数 `rules_version`；默认仍为 `v1`，原有 Notebook 的调用方式可继续复现六规则基线。生成与汇总时要使用相同版本：

```python
orders_v2 = clean_orders(raw_orders, rules_version='v2')
metrics_v2 = summarize_metrics(orders_v2, rules_version='v2')
```

获取标记列表：

```python
flag_cols_v2 = get_review_flag_cols('v2')
orders_v2[flag_cols_v2].sum()
```

函数文件改动后，已经导入模块的 Notebook 内核可能仍保留旧函数。新配套 Notebook 的开头会重新加载模块，再使用更新后的函数。原有两份 Notebook 及 v1 输出保留原样。
