## 代码中在哪里处理多条评价

函数位于 src/reviews_cleaning.py。最需要先读懂的是两个函数。

### select_latest_reviews：筛选每单最新的一条

第一步只计算每单最大提交时间，还没有减少记录：

```python
# 给每行附上同一订单的最大提交时间
latest_time = cleaned.groupby("order_id")[
    "review_answer_timestamp"
].transform("max")
```

第二步才发生筛选：

```python
# loc 只选时间等于该订单最大时间的记录，返回新表
latest = cleaned.loc[
    cleaned["review_answer_timestamp"].eq(latest_time)
].copy()
```

当前每单最新时间没有并列，所以结果每单一行。原始评价工作表仍保留 99,224 行，最新评价表为 98,673 行。这是新表的按规则选取，原始明细没有被删除。

### aggregate_order_reviews：把全部记录汇总成每单一行

```python
stats = cleaned.groupby("order_id", as_index=False).agg(
    review_record_count=("review_id", "size"),      # 每单全部评价记录数
    low_score_record_count=("is_low_score", "sum"), # 每单低评分记录数
    any_low_score=("is_low_score", "any"),         # 是否至少出现一次低评分
)
```

随后把这个汇总与最新评价按 order_id 连接，得到 order_reviews。validate='one_to_one' 检查两侧唯一性，真正减少多行的是前面的筛选和聚合。

例如，订单先 2 分、后 5 分，订单级结果保存：

| low_score_record_count | 1 |
| latest_review_score | 5 |
| latest_is_low_score | False |
| any_low_score | True |

## 记录计数、规则与缺失

低评分记录有 14,575 条，包含 14,533 笔订单。40 笔订单各有 2 条低分记录，1 笔有 3 条，因此共多出 42 条记录，涉及 41 笔多次低分订单。

最新有效评分作为订单主口径，任意一次低评分作为对照口径；均定义 1～2 分为低评分。两种规则得到 14,494、14,533 笔低分订单，对应 14.69%、14.73%，分母均为 98,673 笔有有效评价的订单。

39 笔规则不同的订单属于口径差异，不能据此认定运营挽回了 39 笔订单。样本订单 059bbeb3477ed66fd7e670c3f879009a 先在 2017-08-01 提交 2 分，再在 2017-08-04 提交 5 分。

| latest_is_low_score | 含义 |
| --- | --- |
| True | 最新有效评分为 1 或 2 分 |
| False | 最新有效评分为 3～5 分 |
| 缺失 | 该主表订单没有匹配评价，无法判断 |

无评价的 768 笔订单保留，布尔列使用可空 boolean，评分和计数列使用 Int64。不能把无评价填成非低分。

## 异常时间的处理边界

- 非空但无法解析的时间：停止核查。
- 创建日期缺失：明细保留，提交间隔未知；若提交时间已知，仍可以排序。
- 提交时间缺失或早于创建日期：明细保留标记，选择最新评价前停止核查，不猜测它是不是最新。
- 最新提交时间并列：停止，先明确取值规则，避免任意选择第一行。
- 长提交间隔：保留原值和样本。本数据最大约 518.70 天，原因仍待核查。

当前真实数据不存在前三类缺失/倒置以及最新时间并列问题；这些边界保护用于避免新数据悄悄改变结果。
