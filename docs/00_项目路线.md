# 项目路线

## 业务定位

假设你为电商平台运营负责人提供分析。负责人需要了解经营变化、定位履约与体验问题，并安排卖家治理和客户运营优先级。这里的业务角色是分析场景设定，不代表曾在 Olist 任职或与其开展真实业务合作。

项目名称：**Olist 电商经营与履约优化分析**。

主问题及对应动作：

| 问题 | 分析方法 | 最终支持的动作 |
| --- | --- | --- |
| 销售额变化主要来自订单数还是客单价？哪些品类、地区贡献了变化？ | 趋势、环比、贡献分解、Pareto | 经营复盘与资源关注清单 |
| 哪些订单履约慢？延迟程度与差评如何关联？ | 分位数、延迟分箱、分层对比、区间估计、逻辑回归关联分析 | 履约问题排查与验证方案 |
| 哪些卖家同时影响较多订单且体验较差？ | 规模与体验双维度分层、K-Means、稳定性检查、PCA 可视化 | 带样本量及证据的卖家治理清单 |
| 哪类客户在相同观察期内更容易复购？ | RFM、首购 cohort、固定 30/60/90 天窗口 | 客户运营假设及后续实验设计 |

分析中区分“发现相关性”“提出建议”“设计验证”“已实现收益”。本项目能做到前三类，历史静态数据本身不能证明执行建议后的提升。

讲解节奏：说明业务问题 → 写最小可运行代码/SQL → 解释关键语句 → 检查结果 → 你用自己的话复述 → 再进入下一阶段。

## Power BI 的 8 页设计

1. **经营总览**：商品成交额、订单数、客单价、交付率、延迟率、差评率；明确时间和状态筛选。
2. **增长拆解**：月度趋势、订单与客单价贡献、关键时期变化；展示数据边界。
3. **品类与地域**：品类结构、地区贡献、运费负担；商品粒度金额与订单口径分开。
4. **履约时效**：审批、交承运商、运输各阶段耗时及 P50/P90；地区差异。
5. **评价体验**：评分结构、延迟分箱与差评关联、样本量及分层说明。
6. **卖家分层与治理**：规模、履约、体验、聚类/规则分组、优先跟进名单；多卖家订单的归因限制。
7. **客户分群**：RFM、单次与重复购买客户、贡献分布及运营假设。
8. **复购与 Cohort**：首购月 cohort、月度复购与固定窗口复购，未成熟窗口留空。

## 建模与指标约定（初稿，后续按数据验证）

- 原始层保留原值；清洗层记录处理；分析层明确每张表粒度；Power BI 使用事实表与维度表，保持事实表内粒度一致。参考 [Microsoft 的星型模型说明](https://learn.microsoft.com/en-us/power-bi/guidance/star-schema)。
- 订单主表一行一个订单。商品、支付、评价先在各自粒度处理，不能直接连成一张大表后求和。
- `customer_unique_id` 用于识别数据中的同一客户，`customer_id` 用于与订单关联。该身份标识不等于对现实世界自然人的完全识别。
- 金额单位按数据集为巴西雷亚尔 BRL。区分商品金额 `price`、运费 `freight_value`、支付额 `payment_value`；这些值不能直接当平台收入或利润。
- 经营主口径先拟为已交付订单商品金额；全部下单、取消、在途单独看。客户购买行为使用哪种状态以及何时算复购，进入客户阶段前明确，不把交付日状态与下单事件混用。
- 延迟先拟按日期比较：实际送达日期晚于预计送达日期，分母是已交付且两日期有效的订单；同时报告缺失数量。
- 差评先拟为 1–2 星订单占有效评价订单的比例；同订单多评价需先定义取值规则，不能随意去重。
- 首版月度经营比较使用 2017-01 至 2018-08。2016 年的记录集中在少数月份，2018-09 与 2018-10 合计仅 20 单且没有已交付状态。全量覆盖查询保留观测到的每月首末下单时间。
- 历史数据的 RFM 基准日和 cohort 观察截止日需根据数据窗口冻结，不能使用电脑今天的日期；完整复购窗口不能直接由最晚一条稀疏订单推断。
- K-Means 前检查偏态、缩放、异常值与样本量，比较多个 K 和随机种子，检查簇规模及解释性。PCA 只辅助展示并报告解释方差，不把二维投影当完整证据。
- 延迟与差评采用订单级分析；控制品类、地区、时间等可观测差异后仍只解释统计关联。实际延迟不可用于声称“下单时预测”的模型。
- 卖家评价涉及多卖家订单时，订单整体评价不能直接视为每个卖家的独立评价；先报告单卖家子样本，多卖家另列并做敏感性检查。
- 数据没有访问、曝光、营销触达、成本、库存和实际运营干预记录，不据此计算访问转化率、获客成本、利润、缺货率或声称已验证的提升。
