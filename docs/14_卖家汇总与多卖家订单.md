# 卖家第三步：卖家汇总与多卖家订单

第十五份 Notebook 的三个理解题已核对正确。补入卖家属性后仍是一行一条商品明细；同一卖家在一笔订单中可能有多条明细，因此明细行数可能大于不同订单数。金额控制不一致时，应查原因，不能直接改金额凑平。

现在打开 notebooks/16_卖家汇总与多卖家订单.ipynb。七个代码单元可从原表独立运行，本课开始真正按卖家聚合。

## 从明细到卖家

| 输出 | 一行代表什么 | 主键 |
| --- | --- | --- |
| items_with_sellers | 一笔订单中的一条商品明细 | order_id + order_item_id |
| seller_summary | 一个卖家的销售汇总 | seller_id |
| order_seller_pairs | 一笔订单与一个卖家的关系及明细数 | order_id + seller_id |
| seller_profile | 一个卖家的汇总，附地区属性 | seller_id |

完整销售明细保留。groupby + agg 生成新的汇总表，不是按卖家删除重复明细。

| 汇总字段 | 方法 | 解释 |
| --- | --- | --- |
| item_line_count | order_item_id 的 size | 明细行数 |
| order_count | order_id 的 nunique | 该卖家涉及的不同订单数 |
| product_count | product_id 的 nunique | 该卖家销售过的不同商品 ID 数 |
| goods_amount_cents | price_cents 的 sum | 商品金额，整数分 |
| freight_amount_cents | freight_cents 的 sum | 运费，整数分 |

size 统计组内行数，nunique 在组内统计不同值数。同一商品有多条明细时，不同商品数也不等于明细数。

## 哪些量可以直接跨卖家相加

每条明细只有一个 seller_id，因此按卖家汇总后，明细数量、商品金额与运费可以直接相加核对。

| 项目 | 来源明细 | 卖家汇总 | 差额 |
| --- | ---: | ---: | ---: |
| 商品明细行数 | 112,650 | 112,650 | 0 |
| 商品金额（分） | 1,359,164,370 | 1,359,164,370 | 0 |
| 运费（分） | 225,190,954 | 225,190,954 | 0 |

seller_summary 只有 3,095 行，通过 item_line_count 求和核对明细数。汇总表行数变少并不表示来源记录丢失。

这仍然是全量商品明细、全部订单状态的销售基线，没有冻结正式分析窗口，也没有筛选已交付订单。金额不能直接称为已交付成交额、平台收入或利润。

## 不同订单数为什么不能直接跨卖家相加

| 订单 | 卖家 |
| --- | --- |
| A | 甲、乙 |
| B | 甲 |

甲涉及 2 个订单，乙涉及 1 个订单，两者合计 3；全体不同订单只有 A、B 两个。

本批原始数据检查结果：

| 指标 | 数量 |
| --- | ---: |
| 商品明细覆盖的全体不同订单数 | 98,666 |
| 各卖家不同订单数之和 | 100,010 |
| 订单＋卖家关系数 | 100,010 |
| 单卖家订单数 | 97,388 |
| 多卖家订单数 | 1,278 |
| 相对全局订单计数多出的关系数 | 1,344 |
| 单个订单最多卖家数 | 5 |

注意 98,666 是有商品明细的订单数，不是订单主表全部 99,441 笔订单。两个数字的样本范围需要区分。

order_seller_pairs 按订单＋卖家组合聚合，item_line_count 保留每个组合对应的明细数量。核对时：

- 卖家 order_count 合计应等于订单＋卖家关系表行数。
- 关系表的 item_line_count 合计应等于完整明细数。
- 关系表覆盖的不同订单数应等于完整明细覆盖的不同订单数。
- 一个订单有 k 个卖家，相对全局只计一次，多出的关系数为 k−1。

| 每单卖家数 | 订单数 |
| --- | ---: |
| 1 | 97,388 |
| 2 | 1,219 |
| 3 | 54 |
| 4 | 3 |
| 5 | 2 |

因此 1,278 笔多卖家订单与 1,344 对额外关系不是同一个指标。

不同商品数也要看去重范围：各卖家的 product_count 合计为 34,448，全局不同商品 ID 为 32,951，因为有商品 ID 在多个卖家下出现。不能把组内去重计数默认当成可跨组相加的全局去重计数。

## 补回卖家属性

seller_summary 与 sellers_clean 都是一行一个 seller_id，因此这次关联使用 one_to_one。补入地区后，seller_profile 仍是一行一个卖家，指标保持原值。

本课只建立规模与销售基线。后续计算卖家履约或评价指标时，还要明确订单状态、时间窗口与多卖家订单的归因规则。
